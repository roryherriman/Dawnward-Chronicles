# v0.3 M1: Character Foundations data layer (scope, acceptance criteria, test plan)

Status: **for review. Not authorised for implementation.** When authorised, M1 is built on a new branch `feat/v0.3-character-foundations` from `main`. Nothing is pushed, merged or published without approval.

## Goal
Add the **Source / Interpretation / Canon** data foundation that every later v0.3 milestone builds on: the wizard, TRP3 import, review flow, write test and story prompts. M1 is a **data and engine milestone**. It changes no existing behaviour, adds no window UI, and doesn't touch TRP3.

## In scope

### 1. Schema v3 (additive migration v2 → v3)
Each character (real, simulation and import backups) gains:

| Key | Purpose |
|---|---|
| `sources = { current = <id or nil>, versions = { … } }` | Verbatim biography versions |
| `interpretations = { … }` | Open proposals (candidates and insights) |
| `interpretationKeys = { [key] = { status, at } }` | Memory of rejected and promoted proposals, so they aren't suggested again |
| `facts = { … }` | Canon |
| `wizard = {}` | Reserved for M3. Present so v0.3 needs no second migration. |

- The database gains nothing else.
- `Migrations.steps[2]` only adds empty containers. Fields, family, history, journal, journal keys, theme, IDs, timestamps and import backups are untouched.
- **Schema v3 is frozen when v0.3 is released.** Until then, fields may be added *within* v3 for later v0.3 milestones, because no v3 data exists outside development.

### 2. Limits (named constants, one place: `Schema.LIMITS` / `Schema.FOUNDATION`)
| Constant | Value | Behaviour at the limit |
|---|---|---|
| `facts` | 200 approved facts | Adding is refused with an explanation. Canon is never removed automatically. |
| `pending` | 300 open interpretations | Proposing stops, and the caller is told |
| `keyMemory` | 1,000 remembered keys | Oldest dropped first |
| `bioVersions` | 3 biography versions | Oldest *earlier* version dropped. **The current version is never dropped.** |
| `bioBytes` | 16,384 bytes per version | Capture is refused (never truncated) |
| `statement` | 300 bytes | Text is cleaned and capped like other long fields |
| `excerpt` | 300 bytes | Truncated at a UTF-8 boundary (an excerpt is a quote, not canon) |

### 3. `Core/Facts.lua` (canon)
- **Category registry (data):** origin, relationship, motivation, fear, belief, trait, event, place, other, each with `id`, `label` and `order`.
  - Unknown category IDs in loaded data are kept if they are well-formed (`^[a-z_]+$`, up to 24 bytes) and **displayed** under Other.
  - New facts must use a registered category.
- **Fact record:** `{ id, category, statement, subject?, visibility = "private", provenance, createdAt, updatedAt? }`.
  - `id` comes from the character's shared `nextId`, so IDs stay unique across all lists.
- **Provenance:** `{ origin, sourceId?, sourceVersion?, ref?, excerpt?, interpreted, interpretationKey? }`, where `origin` is one of trp3-field, trp3-biography, paste, written, answers, profile, journal, decision, player.
- **API** (pure, returns `ok`/`item` or `nil, reason`):
  - `Add(char, values, provenance, now)` (player-authored facts);
  - `Update(char, id, values, now)`;
  - `SetVisibility(char, id, level, now)`;
  - `Remove(char, id, now)`;
  - `ByCategory(char)`;
  - `Count(char)`.
- **Single entry point into canon:** only `Facts.Add` (player action) and `Interpretations.Promote` (which calls the internal `Facts.AddFromInterpretation`) create facts. An architecture test enforces this.

### 4. `Core/Sources.lua` (verbatim biographies)
- **Capture:** `Capture(char, kind, text, meta, now)`, where `kind` is trp3, paste, written or answers.
  - Stores the text **exactly** (only the size limit is checked, nothing is cleaned).
  - Computes a content hash (Adler-32 plus the length).
  - **Identical text to the current version stores nothing new** and returns the existing version.
  - A new version becomes current; at most 3 versions are kept.
- **Read:** `Current(char)`, `Versions(char)`, `Get(char, id)`.
- **Display helpers (pure; they never modify the stored text):**
  - `StripTags(text)` removes TRP3 text tags: `{h1}…{/h1}`, `{p}`, `{p:c}`, `{col:xxxxxx}`, `{/col}`, `{img:…}`, `{icon:…}`, `{link*…*…}` (keeping the link text), and unknown `{…}`.
  - `Paragraphs(text)` and `Sentences(paragraph)` give an approximate split: sentence-ending punctuation followed by whitespace, ellipsis handling, a short list of common abbreviations, and CJK sentence punctuation (`。！？`). Tests document the known limits.

### 5. `Core/Interpretations.lua` (proposals)
- **Record:** `{ key, kind = "candidate"|"insight", category, statement, origin, sourceId?, ref?, status = "open", createdAt }`.
- **Keys:**
  - `Interpretations.Key(origin, category, statement)` combines the origin and category with the normalised statement text (lower case, collapsed spaces, no punctuation).
  - Proposing with a key that is already open, rejected or promoted does nothing and returns `"known"`. That's how re-imports avoid duplicates (approved decision 8).
- **API:**
  - `Propose(char, values, now)`;
  - `Reject(char, key, now)`;
  - `Promote(char, key, edits, now)`: applies the player's optional edits, creates the fact with provenance `interpreted = true` and `interpretationKey = key`, and marks the key promoted;
  - `Open(char)`.
- **No automatic promotion exists anywhere.**

### 6. Privacy, exports and simulation
- **Defaults:** facts and interpretations default to **private**. Sources have no visibility and are always private.
- **`Projection.Filter`** gains facts, filtered by visibility. Interpretations and sources are **never** part of a projection.
- **Share export:** public facts only.
- **Backup export:** facts plus interpretations plus key memory. Sources only when asked: `/dawnward export backup biography`, which can be combined with `secrets`.
- **Import** (backup restore, existing undo slot):
  - Secret facts carry over exactly as secret profile fields and entries do today.
  - **When the backup has no sources, the current sources are kept** (carried over), so restoring a backup never discards a stored biography.
  - Key memory is merged.
- **Simulation:** all new data lives in the active database, as everything else already does.
- **Older exports:** v0.1 and v0.2 exports still import, with empty foundation containers.

### 7. Minimal commands (for testing and advanced users; no window UI in M1)
All new commands go through `Actions`: read-only checks, and no empty character created on failure.

| Command | Effect |
|---|---|
| `/dawnward fact list` | Lists facts grouped by category, with visibility |
| `/dawnward fact add <category> <statement>` | Adds a player fact (private) |
| `/dawnward fact vis <#> public\|private\|secret` | Changes a fact's visibility |
| `/dawnward fact remove <#> confirm` | Deletes a fact |
| `/dawnward status` | Gains one line: "Foundations: N facts, M suggestions, biography stored: yes/no" |

## Acceptance criteria
M1 is done when **all** of these hold:

**Migration and saved data**
1. A v2 database migrates to v3, and every v2 value is preserved exactly: fields, family, history, journal, journal keys, theme, IDs, timestamps, import backups and window position.
2. Migration is **idempotent**: loading v3 data again changes nothing.
3. A v3 database opened by a build that only knows v2 is reported as newer and left untouched. This is existing behaviour; it is re-tested.
4. **The real v2 saved data** (a read-only copy) migrates safely in a dry run, as was done for v1 → v2.

**Canon and proposals**

5. Facts are created only by player action (`Facts.Add`) or explicit promotion (`Interpretations.Promote`). The architecture test finds no other code writing to `facts`.
6. New facts and interpretations default to **private**. Invalid categories and visibility levels are refused, with no side effects.
7. Limits behave as specified: 200 facts refused beyond the limit, 300 open interpretations, 1,000 keys with oldest dropped first.
8. **The current biography version is never dropped.** Identical recapture stores nothing. A fourth version drops the oldest earlier version. Text over 16 KB is refused, never truncated.
9. Re-proposing a known key (open, rejected or promoted) adds nothing, so unchanged re-imports create no duplicates.
10. Promotion records provenance: origin, source and version, ref, excerpt, `interpreted = true` and the interpretation key.

**Privacy**

11. Share exports contain public facts only, and **never** sources, interpretations or key memory. This is checked by scanning the export text for planted marker strings.
12. Backups include sources **only** with the `biography` option. Restoring a backup without sources keeps the current sources.
13. Secret facts carry over on backup restore, as other secrets already do.
14. Simulation-mode facts and sources never appear in real data, and the reverse.

**Display helpers**

15. `StripTags` and `Sentences` pass the fixture set (§Test plan), including documented imperfect cases. Neither ever modifies the stored source.

**Regression and quality**

16. All existing 180 tests still pass, plus the new ones. luacheck reports 0 warnings, and the hygiene and TOC checks pass, locally and in CI.
17. `Core/` still uses no WoW globals and no `os`/`io` (enforced).
18. No TRP3 function other than the existing read-only status is called (the L2 fake records calls).

**In game (L3 smoke test)**

19. On Classic Era 1.15.9, existing saved data upgrades with no Lua errors. `fact add / list / vis / remove confirm` work and persist through `/reload` and a relog. All v0.2 features behave as before (spot check: journal, character editing, export and import, simulation). Total RP 3 is unchanged.

## Test plan

### L0: static
- luacheck with the existing configuration. New Core files inherit the no-WoW-globals rule.
- The hygiene scan, and the TOC completeness check for the new files.

### L1: unit tests (new spec files)
| Spec | Cases |
|---|---|
| `core_schema_v3_spec` | v2 → v3 preserves a full v2 fixture field by field; idempotent reload; v3 data in a v2 build stays read-only; unknown keys dropped; malformed facts and interpretations repaired or dropped with a report; IDs unique across family, history, journal and facts |
| `core_facts_spec` | Add/update/remove/visibility; category validation; unknown stored category kept but displayed as Other; 200 limit; statement cleaning and capping; `ByCategory` ordering |
| `core_sources_spec` | Byte-identical storage (including tags, newlines and UTF-8); identical recapture is a no-op; version rotation keeps the current; 16 KB refusal; `StripTags` fixtures (each TRP3 tag type, nested `{col}`, links with icons, unknown tags, a literal brace); `Sentences` fixtures (simple, "St. Ilsa", ellipsis, dialogue quotes, CJK `。`, no final punctuation) with expected *approximate* outputs written down |
| `core_interpretations_spec` | Key normalisation (case, spaces, punctuation); a known key returns `"known"`; reject and promote update key memory; promote applies edits and full provenance; 300 open limit; key memory limit and oldest-first drop |
| `core_transfer_spec` (extended) | Share export excludes planted markers in sources and interpretations; backup with and without `biography`; restore without sources keeps current sources; secret facts carry over; v0.2 exports import with empty foundations |
| `core_commands_spec` (extended) | `fact` commands (including confirm and read-only refusal); the status line |
| `architecture_spec` (new) | Scans `Core/*.lua` source text: only `Facts.lua` may assign into `.facts`; only `Interpretations.lua` calls `Facts.AddFromInterpretation` |

### L2: mocked integration
- Addon load from the TOC with v2 saved data, which upgrades to v3 under the WoW mock.
- `fact` commands through `/dawnward`, persisting in the global saved variable.
- Simulation isolation.
- The TRP3 fake confirms no setter or new getter is called.

### Real-data dry run (read-only)
Run the migration against a **copy** of the current v2 `DawnwardChronicles.lua`, as for v1 → v2. Print only structure and counts, never content.

### L3: in-game smoke checklist (short, mandatory)
1. Back up Dawnward and TRP3 saved data (automated, as before), then install the build.
2. Cold start, then log in: no errors, and `/dawnward status` shows the Foundations line.
3. `/dawnward fact add belief Protect those who cannot protect themselves`, then `fact list`, then `fact vis 1 public`.
4. `/reload` and relog: the fact is still there with its visibility.
5. `/dawnward export share`: contains the public fact. Then `export backup`: contains it, and **no** biography section.
6. `fact remove 1`, then `fact remove 1 confirm`: asks first, then removes it.
7. A spot check of v0.2: open the journal, add an entry, edit a character field, toggle simulation, check Total RP 3 is unchanged.

## Risks specific to M1
| Risk | Mitigation |
|---|---|
| Sentence splitting quality | Documented as approximate; fixtures pin behaviour; display-only |
| Saved-data growth from biographies | 3 × 16 KB limit; sources kept out of share exports, and out of backups by default |
| Schema v3 changes during v0.3 | Freeze at release; dev builds only in the meantime |
| Accidental canon writes from future code | The architecture test fails the build |
