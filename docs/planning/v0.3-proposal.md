# v0.3 proposal: Character Foundations and Story Intelligence

Status: **proposal for review. Nothing is implemented.** It builds on `docs/STORY_ARCHITECTURE.md` and narrows it to what fits one small, testable release.

## Goal
Give every character a small set of **approved facts**, their *canon*, whether the character comes from a long Total RP 3 biography, from text written in Dawnward, or from nothing at all. Then use those facts for one modest, visible personalised feature.

| Starting point | v0.3 path |
|---|---|
| Existing TRP3 character with a biography | Read the profile (read-only), keep an exact private copy of the biography, suggest facts from structured fields, and let the player turn biography sentences into facts |
| History written inside Dawnward | The existing profile, family and history become fact sources, plus anything pasted in |
| No history yet | A short set of optional guided questions; journal milestones keep adding to the story |

## What can realistically be done inside WoW (Classic Era, Lua 5.1)

| Possible | Not possible, or not reliable |
|---|---|
| Reading TRP3 data that is already in memory, in the same game session | Understanding arbitrary free text. Lua 5.1 has no language model, its patterns work byte by byte, and `%a` doesn't match accented letters. |
| Storing tens of kilobytes of text in SavedVariables | Reading files on disk, using the network, or running AI |
| Splitting text into paragraphs and sentences (approximately: abbreviations and odd punctuation will sometimes split wrongly) | Reading the clipboard directly; pasting only works through an edit box |
| Reliable mapping of **structured** TRP3 fields (age, birthplace, residence, personality traits with values, misc fields such as pronouns) | Knowing which words a player has *selected* in an edit box: there is no portable API for that, so the design never depends on it |
| Simple, labelled hints (kinship words like "mother" or "brother", "born in …", repeated capitalised names), shown as *possible* only | Telling who a pronoun refers to, sarcasm, flashbacks, or what is true versus a lie the character tells |
| Picking from packaged story-prompt templates with conditions on approved facts | Generating new story text |

**Conclusion:** structured data can be *extracted*. Free text can only be *offered to the player* sentence by sentence, with optional hints. Everything becomes canon only through the player.

## TRP3 access (read-only, version-gated)

| Data | How | Stability |
|---|---|---|
| Name, title, race, class, icon | Public getters (already used) | Public API |
| Age, birthplace, residence, eyes, height, misc fields (pronouns and others), personality traits | `CurrentUser:GetCharacteristics()`: a **public** method that returns TRP3's live table, so we deep-copy it at once | Public method; the field names come from the audited 3.4.1 source |
| Preset trait names (Chaotic ↔ Lawful, and the other 10 presets) | Stored by TRP3 as numbers only. Dawnward ships its own English name list, checked against 3.4.1. | Version-specific, gated by version |
| About / biography text (templates 1–3) | `CurrentUser:GetInfo("about")`. TRP3's source marks this for deprecation. | **Internal-leaning: needs your approval.** Only for audited versions; unknown versions fall back to pasting. |

- **Never written to.** No setters, no TRP3 events fired, nothing stored back.
- **A paste path works everywhere.** The player can paste a biography from any source (TRP3's editor, another RP addon, a document, or text drafted with AI elsewhere). That covers unknown TRP3 versions and players without TRP3.
- **Profile binding.** The player confirms "this TRP3 profile is this character" once. Dawnward refuses to read TRP3's default profile as a source, because its ID changes every login.

## Data model: schema v3 (additive migration)

```
character.facts      = { { id, category, statement, subject?, tags?, provenance, status, visibility, createdAt } }
character.sources    = { { id, kind = "trp3" | "paste" | "answers", capturedAt, ref, text } }   -- private, capped
character.rejected   = { [suggestionKey] = timestamp }   -- capped; dismissed suggestions are not shown again
```

- **Categories** (fixed and small): `origin`, `relationship`, `motivation`, `fear`, `belief`, `trait`, `event`, `place`, `other`.
- **Status:** `suggested` → `approved` (canon) or `rejected`. Edits always produce `approved`.
- **Provenance:**
  - `source`: trp3-field, trp3-biography, paste, answers, profile, journal or player;
  - `interpreted`: true when the statement summarises its source rather than quoting it;
  - `ref`: which source and which sentence.
- **Original text** is kept exactly as it was in `sources`. A new capture of the same TRP3 profile replaces the previous one only when the text changed, and only one per source is kept. Size cap: 16 KB per source and 3 sources per character; over the cap, capture is refused with an explanation. Nothing is truncated silently.
- **Privacy:**
  - Facts start **private**.
  - Sources are always private and never included in share exports.
  - Backups include facts. They include sources only on request, since sources can be captured again.
- **Simulation:** facts, sources and suggestions live in whichever database is active, so experiments never touch real canon.
- **Existing fields stay:** profile, family and history are unchanged, and they can *suggest* facts without being duplicated automatically.

## Modules (all small and separately tested)

| Module | Layer | Responsibility |
|---|---|---|
| `Core/Facts.lua` | Core | Create, edit, approve, reject and delete facts; caps; queries by category and subject |
| `Core/Sources.lua` | Core | Store and replace verbatim sources; split text into sentences (approximate, tested on known examples) |
| `Core/Suggest.lua` | Core | **Deterministic** suggestions with stable keys: structured TRP3 fields → facts; profile, family and history → facts; optional *hints* on sentences. Never creates canon. |
| `Core/Questions.lua` | Core | 6–8 packaged guided questions → suggested facts |
| `Core/Prompts.lua` | Core | Packaged story-prompt templates with conditions on approved facts (see M5) |
| `Integrations/TRP3/Reader.lua` | Integration | Version-gated, read-only capture of characteristics and About. Returns copies only. |

## UI: within the existing three sections

- **Character section:** gains one area, *Foundations*, below the profile. It shows:
  - approved facts grouped by category, each with Edit, Delete and visibility;
  - one line, "Suggestions to review (N)", which opens a simple one-at-a-time review: **Approve**, **Edit then approve**, **Reject**, **Skip**;
  - a few small buttons: "Read my TRP3 profile", "Paste a biography", "Answer a few questions".
- **Biography view:** the stored text as a list of sentences. Clicking a sentence offers "Make this a fact…" with the sentence pre-filled and a category to pick.
- **Story section:** v0.3 replaces the empty state with **story prompts** (M5). These are not decisions yet.
- **Settings:** the TRP3 profile binding is added to the existing read-only TRP3 area.
- **No new tabs, no dashboard, no counts beyond "Suggestions (N)".**

Order note: M1–M4 deliver all three starting points **without any TRP3 internal access**. M5 is separate, so it can be postponed if you prefer not to rely on `GetInfo("about")`.

## Explicitly out of scope for v0.3
- No decision engine or story choices with consequences (v0.4). No personality changes.
- No writes to TRP3, ever, in this release.
- No AI integration and no external tools. Text drafted elsewhere can only be *pasted* and reviewed.
- No claim that suggestions understand free text. Hints are labelled "possible" and can be turned off.

## Decisions for you
1. **TRP3 biography reading (M5):** may Dawnward use `GetInfo("about")` (deprecated, but on the public `CurrentUser` object), version-gated to audited 3.4.1, or should v0.3 rely on the paste path only?
2. **Story prompts (M6):** include them in v0.3 as the first personalised feature, or keep Story empty until the decision engine?
3. **Biography copies in backups:** facts are always included. Should the stored sources be included by default, or only on request (proposed: on request)?
4. **Fact categories:** is the proposed list of nine right for your characters?
